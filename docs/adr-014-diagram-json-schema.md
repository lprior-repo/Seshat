# ADR-014: Diagram JSON Schema

## Status

**Accepted** (2026-03-23)

## Context

Seshat needs a stable, versioned JSON file format for persisting diagram documents. The format must be human-readable, tooling-friendly, support schema evolution, and be AI-friendly for CLI agent consumption and generation.

We already have several foundational pieces in place. The `DiagramDocument` type in `diagram_models/src/document/mod.rs` uses serde for serialization. The `physical_io` module handles file operations with validation and migration support. A JSON Schema draft-2020-12 specification exists at `diagram_models/src/diagram.schema.json`. The migration system in `diagram_models/src/physical_io/migration.rs` handles version upgrades.

The challenge is to ensure these pieces work together coherently with explicit contracts, clear module boundaries, and comprehensive validation that prevents invalid data from ever entering the domain layer.

## Decision

### File Extension and Naming

We use `.seshat.json` as the file extension. The double extension serves a critical purpose: any JSON-aware tool (IDEs, diff tools, grep) can open and inspect these files, while the `.seshat` prefix clearly identifies them as our format. Filenames may contain alphanumeric characters, dashes, underscores, and spaces, but must avoid reserved filesystem characters like `:`, `?`, `*`, `"`, `<`, `>`, and `|`.

### Schema Versioning

The current schema version is `2`, stored in a top-level `version: integer` field. We support migrations from versions `0.9` and `1.0` to the current version, automatically adding a `revision: 0` field if missing during migration. Files with versions below `0.9` are rejected as too old, and files with versions above `2` are rejected as future versions we don't yet understand. This approach ensures backward compatibility while maintaining a clear upgrade path.

The migration flow works as follows: when loading a document, we parse the raw JSON, check the version field, run any necessary migrations (currently only v0.9/v1.0 → v2), validate the structure, and finally deserialize into the `DiagramDocument` type. This happens entirely in the `physical_io` module before domain types are constructed.

### Schema Structure

The top-level document contains four required fields: `version` (integer, must be 2), `revision` (non-negative integer, monotonically increasing), `document` (object containing `nodes` and `edges` maps), and `editor_state` (object with UI state).

**Nodes** are keyed by `NodeId` (a non-empty string) and contain properties for position (`x`, `y`), dimensions (`width`, `height`), appearance (`kind`, `icon`, `label`, `style`), hierarchy (`parent`, `dag_rank`), and extensibility (`tags`, `metadata`). All coordinate values must be finite — NaN and Infinity are rejected at the validation boundary. The `metadata` field serves as an extension point for custom properties like `rotation` and `visibility`.

**Edges** are keyed by `EdgeId` and reference source and target nodes by their IDs. They include routing information (`bend_points`, `arrowType`), styling (`style`, `thickness`, `color`), and optional port anchors for precise connection points. The `label_offset_t` field controls label placement along the edge path (0.0 = start, 1.0 = end).

**Editor State** captures UI concerns like camera position (`camera_x`, `camera_y`, `zoom`), grid settings (`grid_size` must be in [10.0, 100.0], `snap_to_grid`, `show_grid`), selection state (`selected_items`, `edit_mode_target`), and theme preference.

### Module Boundaries

The schema touches multiple modules with clear separation of concerns. The `document/` module owns the domain types (`Node`, `Edge`, `EditorState`) and their serde implementations. The `physical_io/` module handles file I/O, validation, and migration — it's the boundary layer that ensures only valid data reaches the domain. The `validation/` module defines validation result types. The `diagram.schema.json` file is the single source of truth for the JSON Schema specification.

This separation means that `physical_io::load_document()` performs all validation before constructing domain types. Invalid JSON, missing fields, type mismatches, and non-finite floats are all caught before a `DiagramDocument` is ever created.

### Error Taxonomy

The `physical_io::Error` enum covers all failure modes at the I/O boundary. `IoError` wraps filesystem failures. `ParseError` indicates invalid JSON syntax. `MissingField` and `TypeMismatch` flag structural problems. `UnsupportedVersion` rejects files that are too old or too new. `SerializationFailed` catches issues when writing, including the discovery of NaN/Infinity values. `RecursionLimitExceeded` prevents stack overflow on deeply nested malicious JSON.

At the domain level, `DocumentError` handles business rule violations like referencing non-existent nodes or edges.

### Validation Rules

On load, we validate: JSON syntax validity, maximum depth of 100 levels, root must be an object, `version` field must exist and be a number, `document` must contain `nodes` and `edges` objects, no null node or edge entries, and `metadata` must be an object if present.

On save, we validate: all floats are finite (no NaN, no Infinity), and the serialization depth doesn't exceed 100 levels.

These validations happen in `validate_structure()`, `validate_document_floats()`, and `validate_serialization()` functions within `physical_io/mod.rs`.

### Contracts

The design-by-contract specification in `diagram_models/src/lib.rs` defines the guarantees:

**Preconditions** that must be true before operations: node positions must be finite, node dimensions should be positive, edge references must point to valid NodeIds at the domain level, and document revision must be non-negative.

**Postconditions** that must be true after operations: NodeId/EdgeId newtypes wrap non-empty strings, `OrderedFloat` maintains total ordering, and serialization roundtrips preserve document equality.

**Invariants** that must always be true: each Node has a unique NodeId within a document, each Edge has a unique EdgeId, node positions are relative to parent (or world space if no parent), and document revision monotonically increases.

The `load_document()` function has explicit contracts: the file must exist, be readable, contain valid UTF-8, and be valid JSON. On success, it returns a document with `version == 2`, all finite floats, and non-empty ID strings. The `save_document()` function requires a writable parent directory and a document with only finite floats. On success, the file contains valid JSON that roundtrips correctly.

### CLI Integration

The schema integrates with the AI CLI through three main commands. `seshat validate --input diagram.seshat.json` validates a file against the schema. `seshat show --json` outputs the current state as JSON. `seshat apply --input patch.json --base-revision 42` applies a patch with optimistic concurrency control via the revision check.

## Consequences

### Positive

Any JSON tool can open these files, making them accessible without special software. IDEs can validate against the `$schema` field. The version field provides a clear migration path. Rust types enforce invariants at compile time. The machine-readable schema enables AI agents to generate and consume documents correctly.

### Negative

Schema migrations require ongoing maintenance as the format evolves. Unknown fields in future versions are currently rejected rather than preserved, though this can be enhanced later.

### Risks

Very large diagrams (3000+ nodes) may impact parse time, suggesting a potential future need for streaming parsers. The JSON Schema and Rust types could drift apart if not kept in sync, though using the schema file as the single source of truth mitigates this.
